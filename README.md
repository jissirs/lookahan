# lookahhan

เว็บแอปจัดการ stock วัตถุดิบ เมนู และออเดอร์สำหรับร้านอาหาร (UI ภาษาไทย)

สถานะ: อยู่ระหว่างพัฒนา มีกรณี workflow ที่ยังต้องแก้ก่อนใช้งานจริง ดู [ปัญหาที่ยังพบและวิธีทดสอบ](KNOWN_ISSUES.md)

การใช้งานร้านอาหารตามสั่งหนึ่งร้าน สิทธิ์พนักงาน ตัวเลือกต่อจาน การรับเงิน/ปิดเงิน การสำรอง และ deployment: [คู่มือใช้งานจริง](PRODUCTION.md)

```
lookahan/
├─ frontend/   React 19 + Vite — หน้าเว็บทั้งหมด (ดึงข้อมูลจาก Backend)
└─ Backend/    Flask + SQLAlchemy — API ครบ ต่อกับหน้าเว็บแล้ว ใช้ SQLite หรือ MySQL ออนไลน์ (ไม่มีข้อมูลจำลอง ฐานข้อมูลเริ่มว่าง)
```

## เริ่มใช้งาน (หน้าบ้าน)

```bash
cd frontend
npm install
npm run dev      # เปิดที่ http://localhost:5173  (ต้องรัน Backend ไว้ก่อน)
```

รายละเอียดสถาปัตยกรรม เส้นทาง (routes) และรูปแบบ API อยู่ที่ [frontend/README.md](frontend/README.md)
วิธีติดตั้งและรัน Backend อยู่ที่ [Backend/README.md](Backend/README.md)

## เกณฑ์สถานะวัตถุดิบ

| สถานะ | pcs | g / ml |
|---|---|---|
| Out of stock | 0 | 0 |
| Critical | 1–5 | 1–500 |
| Low | 6–10 | 501–1,000 |
| Normal | มากกว่า 10 | มากกว่า 1,000 |

เกณฑ์เดียวกันใช้ทั้งหน้า Stock, Dashboard, Statistics, AI และแจ้งเตือน โดย Out of stock มีความเร่งด่วนสูงสุด

## Config ลด stock ของสด

ระบบพยากรณ์เดิมคำนวณวัตถุดิบจากออเดอร์ × จานต่อออเดอร์ × สัดส่วนเมนู × สูตรต่อจาน แล้วแนะนำเติมเฉพาะส่วนที่ขาดจาก stock ปัจจุบัน ไม่มีหน้าใหม่

ตั้งค่าใน `Backend/.env` (ไม่ใส่ก็ใช้ค่าเริ่มต้นด้านล่าง):

```env
FRESH_STOCK_CATEGORIES=Meat,Vegetable,Fruit
FRESH_STOCK_BUFFER_PERCENT=0
FRESH_STOCK_PURCHASE_STEP=1
```

- ของสดไม่บวกของเผื่อ ไม่ปัดยอดซื้อขึ้นทีละ 10 g/ml และไม่ใช้เกณฑ์ Low เป็นยอดที่ต้องซื้อ
- จำนวนจานแบ่งเป็นจำนวนเต็มโดยผลรวมตรงกับพยากรณ์ ลดการซื้อเกินจากการปัดเศษทุกเมนูขึ้น
- ของสดที่ไม่มีเมนูใช้จะถูกนับเป็นของค้างและไม่ถูกแนะนำให้ซื้อเพิ่ม
- ต้องมีสูตรและหน่วยตรงกัน ผลพยากรณ์ไม่รับประกันว่าขายหมดจริง; ล็อตที่ไม่ทราบวันหมดอายุยังถือว่าใช้ได้จนกว่าจะบันทึกทิ้ง
- หลังแก้ config ต้องเริ่ม backend ใหม่


### หน่วยซื้อ ล็อต และรายการซื้อรายวัน

- ใช้หน้า Stock เดิม: เลือกหน่วยสูตร `pcs/g/ml`, หน่วยซื้อเป็นหน่วยเดิม, `kg` (1,000 g), `l` (1,000 ml) หรือ `pack` (ระบุขนาด 1–10,000 หน่วยใช้)
- กรอกราคาต่อหน่วยซื้อเป็นบาทและสตางค์ ระบบเก็บต้นทุนต่อหน่วยใช้ด้วย Decimal 6 ตำแหน่ง และมูลค่ารวม 2 ตำแหน่ง
- รับสินค้าพร้อมเลขล็อตและวันหมดอายุในหน้ารายละเอียดวัตถุดิบ วันหมดอายุใช้ได้ถึงสิ้นวันตามเวลาร้าน; วันถัดไปไม่รวมในสต็อกที่ใช้ทำอาหาร
- ตัดล็อตหมดอายุก่อน (FEFO) และคืนล็อตเดิมเมื่อยกเลิกออเดอร์ สต็อกเดิมถูกจัดเป็นล็อตไม่ทราบวันหมดอายุเมื่อมีการเคลื่อนไหวครั้งถัดไป ไม่มีการแต่งวันหมดอายุย้อนหลัง
- ปุ่มบันทึกของเสียหักทั้งล็อตพร้อมประวัติ; ปิดร้านยังคงใช้ยอดคงเหลือจริงทั้งหมด (รวมล็อตที่ยังไม่ได้นำทิ้ง)
- Statistics เดิมมีแผนซื้อวันนี้/พรุ่งนี้ ใช้ผล AI ที่บันทึกไว้ก่อนเริ่มวัน หรือระบุชัดว่าเป็นค่าเฉลี่ยวันเดียวกันในสัปดาห์จากวันที่จบแล้ว หากไม่มีประวัติไม่แนะนำซื้อโดยแต่งยอดขึ้นมา
- แผนวันนี้หักออเดอร์ที่รับแล้ว แผนพรุ่งนี้หักวัตถุดิบที่คาดว่าจะใช้วันนี้ก่อน และไม่นับล็อตที่หมดอายุก่อนวันใช้งาน การซื้อเป็นแพ็กปัดเป็นแพ็กเต็มพร้อมแสดงส่วนเกิน
- ความแม่นยำใช้เฉพาะผลที่บันทึกก่อนวันเป้าหมายและวันที่จบแล้ว แสดง MAE/WAPE (รวมวันยอดขายศูนย์) และ MAPE เดิม พร้อมเทียบ baseline; ยอดจริงคำนวณใหม่ได้เมื่อออเดอร์ย้อนหลังเปลี่ยน
- การอนุมานวันที่ไม่ขาย: ไม่มีปฏิทินวันหยุดร้าน จึงนับวันไม่มีออเดอร์หลังวันที่เริ่มมีประวัติเป็นศูนย์ ผลที่อิงข้อมูลตัวอย่างยังไม่ใช่หลักฐานความแม่นยำของร้านจริง

อัปเกรดฐานข้อมูลเดิม (จากโฟลเดอร์ Backend):

```powershell
venv/Scripts/python.exe scripts/upgrade_inventory.py          # ดูแผน
venv/Scripts/python.exe scripts/upgrade_inventory.py --apply  # สำรองก่อนแก้โครงสร้าง
```

ต้องหยุด backend ขณะอัปเกรด รองรับ MySQL เดิมและฐานข้อมูลใหม่ เก็บสำรองตารางที่แก้ใน `Backend/.db-backups/` (ไม่เข้า Git) ไม่ลบข้อมูลเดิม รันซ้ำได้ ส่วนฐานข้อมูล SQLite ที่มี schema เก่าต้องใช้การย้ายตารางที่เหมาะสมแยกต่างหาก


### ลบและกู้คืนวัตถุดิบ

หน้า Stock → ⋮ → × → ยืนยัน ลบออกจากรายการใช้งานด้วย `deleted_at` โดยเก็บยอดคงเหลือ ล็อต และประวัติไว้ทั้งหมด ไม่มีการตัดยอดทิ้งอัตโนมัติ ถ้ายังอยู่ในสูตรเมนูหรือออเดอร์สถานะ new/cooking/ready ระบบตอบ 409 พร้อมรายละเอียดที่ต้องจัดการก่อน

เลือก “วัตถุดิบที่ลบแล้ว” ในหน้า Stock → ⋮ → ↶ เพื่อกู้คืน ยอดและล็อตเดิมจะกลับมา (วันหมดอายุไม่เปลี่ยน) ชื่อที่ถูกลบไปแล้วยังสงวนไว้และแนะนำให้กู้คืนเมื่อพยายามสร้างซ้ำ รายการที่ลบไม่อยู่ใน snapshot, การปิดร้าน, สูตรใหม่ หรือแผนซื้อ แต่ประวัติเก่ายังอยู่ในฐานข้อมูล

API: `DELETE /api/v1/ingredients/<id>`, `GET /api/v1/ingredients?deleted=true`, `POST /api/v1/ingredients/<id>/restore` ต้องล็อกอินและจำกัดสาขา รัน `scripts/upgrade_inventory.py --apply` ก่อนเริ่ม backend รุ่นนี้
